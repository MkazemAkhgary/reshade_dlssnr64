# DLSSNR session log — 2026-09-27

Changes made this session. Grouped by the problem each was answering, not
by file. Several are interlocking: read the note under each heading if you
are trying to work out why one exists.

## Composition and the model's edit

### Grade is a strict no-op at defaults

The grade was altering every frame even with every slider at zero, in two
places:

- `PrepareForOutput` ran a highlight roll-off (`knee = 0.75` in linear) that
  compressed everything above sRGB ~0.885. Now gated on `luma_raised`, a
  per-pixel flag set only when the grade actually raised that pixel's luma.
  At defaults the flag is false everywhere and the roll-off never runs.
- The `y > 1e-4` grayscale fallback in the grade body replaced near-black
  pixels with a flat grey, discarding chroma. Replaced with a uniform scale
  using `safe_y = (y > 0) ? y : 1`, so near-black keeps its hue and exact
  black still multiplies to zero.

### Grade runs in an SDR-white normalised space

`ApplyGrade`'s decode/encode pair was normalising to scRGB (1.0 == 80 nits)
in every format. Every operator in the grade assumes 1.0 is SDR white: the
mid-grey pivot `0.2140`, the `saturate()` windows in the shaping weights,
and the `(1 - y)` headroom in Lift and Soft. In backbuffer mode on an SDR
frame this was accidentally correct. In DLSS-output mode with HDR content,
the same sliders acted against the wrong reference and read as "extreme".

The grade's copy of `DecodeToLinear`/`EncodeFromLinear` now normalises to
`kSdrWhiteNits = 100`. The compose's copy is left at the scRGB convention
on purpose: it carries a ratio, which is scale-invariant, and the two
copies would otherwise have to disagree about what the encode means.

### The residual is measured in the graded domain

The compose read `low_in` (graded by `GradeModelInput`) and `low_out` (the
model's edit of that graded image), derived a ratio between them, and
applied that ratio to the *ungraded* `original`. A gamma on the model input
therefore leaked through to the composed HDR, which is the "model raw looks
realistic but composed output doesn't" symptom.

Fixed by applying the same grade to the source before the ratio and
inverting it after. Grade parameters are passed to both composes as new
uniforms at `kGradeSlotBase`, and the forward/inverse operators are now
published as `kGradePrelude` (prepended to both compose passes via a new
`ComputePassDef::prelude` field). The SDR compose got the same treatment;
it needed `ShapeResidualSdr` because its residual is log-space rather than
a per-channel ratio.

Two operators have implicit inverses and iterate: `PreludeShapeInv` (Newton,
4 steps) and the vibrance chroma mode (3 fixed-point steps).

### Inverse tonemap on the model output

`ComposeRatio` now inverts the tonemap on the model's output before deriving
the ratio, so the edit is applied through the curve the model actually saw.
Two bugs surfaced in the process:

- Inverting the model output against the *unbounded source* collapsed every
  clipped highlight to a fixed grey, because `LinearToSrgb` saturates and
  the inverse of a clipped value is the white point. Fixed by inverting both
  sides and taking the ratio between the two inversions.
- Chroma transfer disappeared entirely because `ReinhardInverse` was declared
  `float -> float`, and HLSL silently truncates a float3 argument to its
  `.x` when the parameter is scalar. Now `float3 -> float3`, with a comment
  repeating the reason (the same warning exists on `ReinhardForward`).

## Upscaling quality

### FSR 1.0 EASU and RCAS

Pasted into `kComposeModelOutputHdr`, MIT header preserved. EASU replaces
the bilinear sample of both working-scale images; RCAS is optional
sharpening on the EASU result, gated by `kRcasEnabled`/`kRcasStrength`.
`FsrGatherR/G/B` take a channel selector (0 = model input, 1 = model
output) so one implementation serves both.

Constants live in new `ComputeConstants` regions: `kEasuSlotBase = 36`
(12 floats) and `kRcasSlotBase = 48` (4 floats). `kParamSlotCount` went
from 48 to 52 to hold them, with the appropriate static_asserts.

RCAS reads its four neighbours from a bilinear sample, not a second EASU
call. The neighbours are only used for the local-contrast estimate, and
four extra EASU invocations per texture cost more than the sharpening is
worth.

UI: a "Sharpening" sub-section under each pass, with enable and strength.

## Resource lifetime

### The grade had one scratch slot for two callers

`GradeModelInput` and `GradeModelOutput` ran at different resolutions when
working scale was below 1.0, and both used the same scratch slot. Each
call disposed the other's texture and created a new one, every frame, twice.
This was the stutter on working-scale changes and the crash when both
grades were enabled.

Fixed by assigning one slot per caller: `kGradeScratchSlotA` for the input
grade, `kGradeScratchSlotB` for the output grade. `GradeInPlace` takes a
slot parameter; `ScratchMatches` exists for the general case but the
callers no longer use it.

### Retired resources were not drained

`PassResources::Dispose` routes replaced resources into `DlssGuides`' retire
queues via `RetireResourceCallback`. Those queues were only drained from
`PassSession::SubmitAndWait`, which runs in the Present stage. A frame with
only PostDLSS passes never reached it, so every working-scale change leaked.

Fixed by draining both queues at the end of `OnPresent`. The pre-drain
count is logged so the amounts are visible, and a diagnostic reports what
was released.

### Dispatch ring sizing

`kMaxDispatchesPerFrame` was `3 * 5 + 2`. Counting the Release stage's
backbuffer grade, worst case is `3 * 5 + 3`. The assertion in
`pass_session.cpp` was updated with it.

## HDR metering

### Three histograms, not one

`BuildHistogram` now writes three 256-bin histograms into one 768-entry
buffer: full frame, depth-filtered (sky excluded), and skin. The CPU side
picks which one drives the exposure median and always uses the full-frame
one for the white point.

Why three: the depth filter can leave too little of the frame to measure
from, and the skin detector can find nothing. With two, the metering got
stuck on a stale value in either case. The full-frame histogram is the
fallback that keeps it alive.

Skin detection is a hue test in gamma-2.2 space — 15 to 45 degrees, with a
saturation floor of 0.15 to exclude white and near-white. Graceful on
false positives: a wooden desk in the same hue band just shifts the
measurement slightly.

Sky detection is `d > 0.95` or `d < 0.05`, depending on the guide's
inversion flag. Uses the depth guide already captured for the model.

### Rate cap

Exposure was following bright objects in and out of frame too aggressively.
A per-measurement cap in log2 space now bounds how far the target can move
from the current EMA. Warmup (first ~30 measurements) is exempt, so
convergence at startup is unchanged. New setting `hdr_rate_cap`, slider in
the HDR section. 0 disables the cap and restores the previous behaviour.

New settings alongside it: `hdr_skin_fraction_threshold` (skin priority)
and `hdr_depth_fallback_fraction` (when to give up on the depth filter).

## Residual edit

### Shaping controls

New per-pass `ResidualSettings` fields:

- `chroma_strength` — 0 collapses the edit's per-channel delta to its luma,
  so only brightness moves. The setting for scenes where the model's chroma
  shift reads as wrong.
- `edit_gamma` — sign-preserving curve on the edit's magnitude.
- `highlight_protect` — fades the edit out above SDR 0.7.
- `shadow_protect` — fades the edit out below SDR 0.3.

Applied by `ShapeResidual` (HDR) and `ShapeResidualSdr` (SDR). Both default
to a pass-through. UI under the existing Residual Edit sub-header.

Note: the residual's `kChromaStrength` macro was renamed to
`kResidualChroma` — it collided with the shader parameter macro of the same
name at `gParams[0].y`, and the last definition wins in HLSL. The old name
was silently redirecting the `BlendYCbCr` chroma strength at the wrong slot.

## UI

### Pass tabs

- Renamed to `###` form so the ID is the position and the label can change
  without the tab losing its state. Custom names persisted in
  `PassSettings::custom_name`.
- Pass body is drawn once for `active_pass` below the tab bar, rather than
  from `BeginTabItem`'s return value. That return tracks ImGui's own
  selection, which lags a reorder by a frame — drawing from it showed the
  wrong pass for one frame after a move.
- Reorder buttons (`<` and `>`) deferred to the top of the next frame via
  `g_pending_move`. Applying the permutation mid-loop redrew the tabs to
  the right with the new names and left the current tab's body half-drawn.
- `ApplyPassReorder` re-applies the invariants the pass body assumes:
  pass 0 is the inheritance root with no inherit flags set, and a Present
  pass forces every later pass to Present.
